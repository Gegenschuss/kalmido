# The shared core: how to build a new area

*Since 2.558.0 (stage 1). For developers of Kalmido.*

A new area (meetings, a social media planner, team projects ...) needs **no share table of its own, no check function of
its own and no save path of its own**. It registers its kind of object with the core and uses three calls:

1. `obj_register(...)` once at import (kalmido/core/objects.py)
2. `obj_need(c, uid, kind, id, "view" | "write" | "manage")` in every route that reads or changes an object
3. `obj_write(c, uid, kind, id, body)` to change it (kalmido/core/writes.py)

The rest comes with the core: shares to people, groups and agents (with expiry, through folders of the file store too),
the organisation roles, the version check against lost updates, the history, undo, the trash, the change counter that
tells the other devices, generic routes for the web app and for agents, and a small client for dialogs
(static/js/objsave.js). Old areas move onto the core step by step (stage 2: office and clients, stage 3: calendars and
contacts); stage 1 changes none of them.

## 1. The table

A fragment `kalmido/core/migrations.d/<task>_<x>.py` creates the area's table with at least these columns (names fixed):

```sql
CREATE TABLE IF NOT EXISTS meetings (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  org_id BIGINT REFERENCES orgs(id) ON DELETE CASCADE,          -- NULL = private
  owner_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- private ones go with the account; the core hands an
                                                                -- organisation's to the heir first
  rev BIGINT NOT NULL DEFAULT 1, created_at TIMESTAMPTZ NOT NULL, created_by BIGINT,
  updated_at TIMESTAMPTZ NOT NULL, updated_by BIGINT, deleted_at TIMESTAMPTZ, deleted_by BIGINT,
  title TEXT NOT NULL DEFAULT '', agenda TEXT NOT NULL DEFAULT '', starts DATE);
CREATE INDEX IF NOT EXISTS meetings_trash ON meetings(deleted_at) WHERE deleted_at IS NOT NULL;  -- the trash list
```

Points in time are `TIMESTAMPTZ` (2.760.0, #5311; new tables take real types, checked by the column type lint of #5305). The app
reads them as ISO text in one canonical form (`kalmido/core/pg.py` `ts_canon`: UTC, `+00:00`, microseconds only when there
are any), the same form the older `TEXT` columns hold, and writes the ISO text of `now_iso()` as before. So the answers,
the history, undo and the version check (`expect_updated_at`, `ccf_check` compares both sides canonically) behave alike for
`TEXT` and `TIMESTAMPTZ` tables; an older area moves its columns over in its stage. Never compare such a column with `''`
(`deleted_at IS NULL` / `IS NOT NULL`), and a trigger never takes one as `to_jsonb(row)->>'..._at'` (that text carries the
session's zone, not the canonical form): use `to_char(x AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"+00:00"')`.

Add the table to `kalmido/core/rls.py` TABLES (it has an `org_id`) and to the export lists (`tools/check_export_tables.py`
says where). The core keeps its own data in `obj_history`, `obj_undo` and `obj_revoked`; shares are rows of `fs_shares`
on the object's reference node in the file store.

## 2. Register the kind

```python
from ..core.objects import f_date, f_text, obj_register
from ..core.i18n import N_

obj_register("meeting", "meetings", label=N_("Meeting"), area="calendar",
             fields={"title": f_text(200, required=True), "agenda": f_text(20000, line=False), "starts": f_date()},
             scopes=("calendar", "calendar"), open_url=lambda rid: f"meetings/{int(rid)}")
```

- `fields`: what may be set, each with its cleaner `f(c, value, row) -> clean value` (raise `BadInput`); `None` = the field
  was not sent at creation (its default). Helpers: `f_text`, `f_int`, `f_bool`, `f_choice`, `f_date`.
- `area`: the change counter of `/api/version` (`core/db.py` LV_AREA_KEYS); the other devices reload that area.
- `org_access`: what a full member of the organisation gets without a share: `"edit"` (default), `"view"` or `None`
  (only the owner, the admins and explicit shares).
- `scopes`: the read / write scope an agent's token needs on the agent routes.
- `routes=False` when the area brings its own routes only (then it calls the same functions).
- Hooks for areas with rules of their own (stage 2 / 3): `base_role` (+ its `visible` SQL), `space`, `cap`, `hidden`,
  `dl_area` (an agent's data lock), `undo_scope` (more tables than the main row), `public`, `protect`, `on_trash`, `content`.
- An old area that keeps its own role table and reference kind (stage 6, the projects, `kalmido/lists/lmcore.py`):
  `fsref=False` (the area's registration in files/fsref.py stays; the shares of its node are already in its base role, so
  `obj_role` does not read them again), `share_cols` (its own columns on `fs_shares`, e.g. `list_role` / `list_own`, put back
  by `obj_share_restore`), `on_restore` (the area puts its role table right under its own rules after a restore, or refuses;
  only for the area's own rows of a person / an agent, `list_own = 1` -- any other row of the node takes the core's way, a
  group's own row is refused with 409), the reason `expired` in `obj_revoked` for an own row that ran out,
  `on_revoke` (its part of `obj_revoke_person`) and `list_col` (the column a token's project limit is checked against). Its
  routes call `obj_share(..., extra=..., checked=True)` / `obj_unshare(..., checked=True)` after checking the right and the
  target themselves.
- An old area moving onto the core (stage 3): `members=(table, key column)` names its old member table (one release a
  fallback reader): `obj_revoke_person` takes its rows with the shares when a person leaves / the organisation retires.
  `fs_hooks={...}` replaces keyword arguments of the file store's registration, for a kind the file store knew before the core
  (the address books keep their folder rules: filing and sharing the node stay with who manages it).

The kind is registered with the file store's reference nodes at the same time (files/fsref.py): the object can lie in
folders, and a folder share opens it.

`listed=False` (2.565.0, #4719, the team chat's rooms): the reference node only carries the object's shares. It lies in no
folder, the file store never lists, searches or opens it (fs_ref_rows, fs_ref_hidden_sql, need_node) and it is never filed
(409). The area writes its members with `obj_member_put(c, by, kind, id, key, target, role)` / `obj_member_take(c, by, kind,
id, key, targets, reason)` after its own rule decided (no pool check of the file store: a group conversation spans
workspaces); taken shares land in `obj_revoked`. `obj_share_rows_sql(kind)` reads the live shares in bulk, `obj_gate(c, uid,
kind, row)` is the core's floor for a row the area listed itself (`obj_token_lists(uid)` its token part). With a `cap` hook that gives nothing, the area's base role
is the only role and reads the shares itself (collab/tcxcore.py).

## 3. Who may do what

`obj_role(c, uid, kind, id)` is the one role: `None` < `view` < `edit` < `manage`.

| Who | Private object | Organisation's object |
|---|---|---|
| Its owner | manage | manage (member), view (read-only / guest / accounting now) |
| Organisation admin | - | manage |
| Member | - | `org_access` (edit by default) |
| Read-only member | - | view |
| Guest, accounting | - | only a personal share |
| A share (person, group, agent; folder above too) | view / edit | view / edit (read-only members at most view) |
| An agent | only a share | only a share, only of its own workspace |

On top: another organisation never (404), what `hidden` names never opens through a share (agents and tokens: not even
through the area's own role), an agent's data lock, a token limited to lists, and the trash (only `manage` sees an object
there). `obj_need` turns this into 404 / 403; `obj_visible_sql(c, uid, kind)` / `obj_rows(...)` give the lists. A kind
with a `cap` hook lists only with `obj_rows` (it asks `obj_role` per row): `obj_visible_sql` refuses it with `ValueError`,
because a share there may open less than the SQL would name.

Office documents filed in a folder (`office/docref.py`, decision of #2742, confirmed with #5048): the folder share and the
office groups are two ways in, and the higher one counts for the document itself -- a folder share can lift reading or
changing a draft above the person's office group in the area (also for a member whose group gives the area nothing). The
cap stays the organisation role only (`ofd_cap`: guests nothing, read-only / accounting read). Everything beyond the
document stays with the office groups: finalising, releasing / sending, payments, locking periods, exports and deleting
have no route on the folder way (`/api/fsref/office_doc/<id>`: read, PDF, head fields without status / number / links into
the master data, positions), and a finalised document stays unchangeable (409). Agents only through a share with exactly
them, and then read only.

Losing access is in one place too: `obj_revoke_person(c, uid, org, reason)` (called by the layer accounts through
`core/objhooks.person_revoked`, so accounts never imports the core's modules; `core/objects.py` and `core/writes.py`
belong to the layer domain, `core/objweb.py` to the layer integrations, `LAYER_OF` in `kalmido/__init__.py`) runs when a person leaves an organisation
(their and their agents' shares on its nodes, their team chat rooms there; their objects go to the heir), when a role
goes down to guest / accounting (the open channels they joined), when an organisation retires (every share on its nodes,
every room membership) and when an account is deleted (its organisation objects go to the heir, `upg_heir`, before the
account and its `owner_id` cascade; its private ones go with it; when other people are left but no admin or member who may take them,
the deletion is refused as for calendars, `upg_heirless`). What goes waits 30 days in `obj_revoked`; a manager can put a
share back (`obj_share_restore`). Retiring an organisation takes every share of the file store on its nodes for good:
there is no way back out of the retirement, so after the 30 days those rows are gone (its export has no shares then).

## 4. Saving

```python
row, changed = obj_write(c, uid, "meeting", mid, body())   # rights, lock, version, fields, history, undo, bump
c.commit()
```

- Only the fields sent change; an unknown field is 400.
- `expect_updated_at` in the body = the `updated_at` the client read: another one -> 409 with the current state under
  `current`, nothing written. People may leave it out (old clients); **agents must send it** (400 without).
- Each change: `rev+1`, `updated_at`, `updated_by`, an entry in the history (one person's changes within ten minutes
  merge; an agent's are marked), the title on the reference node, `bump` of the area.
- `obj_space_set(c, uid, kind, id, org_id)` (2.579.0, #4802): the object moves into an organisation or back into its owner's
  own space -- e.g. a saved view an admin shares with everyone of the organisation (members then get the kind's `org_access`).
  'manage', a person; into an organisation as for `obj_create`; out of one only its admin (logged, `accounts/orgout.py`); refused
  (409) while its node carries shares. Register a kind with `org_join="admin"` when only admins may bring its objects into an
  organisation (at creation too): a member's objects of it stay private.
- `obj_create`, `obj_trash`, `obj_restore`, `obj_purge` (only from the trash), `obj_history`, `obj_undo`. `obj_trash` puts the
  object's reference node into the file store's trash with it and `obj_restore` brings that node back, so the folders and
  their searches hide a trashed object like any node in the trash (no extra clause per kind). Should the file store's
  trash empty the node first, the object comes back without its folder place.
- 2.773.0 (#5292): this is THE trash of the core. `children=((table, key column), ...)` in `obj_register` = rows of other
  tables that belong to the object: they go into the trash with it (its `deleted_at`), come back with it (only the ones that
  went with it) and are deleted for good with it. A trash / restore of a person is a step of the list of steps
  (`GET /api/undo`, mode `trash` / `restore`, no copy): taking it back runs `obj_restore` / `obj_trash` with the rights of
  now. `trash_prune=True` lets the core's retention run (`obj_trash_tick`, hourly, `ret_trash_cut` + the switch "trash")
  delete the kind's trash the same way as `obj_purge`; an area with its own run keeps it until its stage moves it.
- 2.784.0 (#5366, stage 4): an office kind that deletes by `deleted_at` registers with `office/okern.py ofk_register(kind,
  table, label, rights area, need)` (no routes, node or listing; the core's role = the office's level `need` in that area)
  and its own routes call `ofk_trash` / `ofk_restore` after their office checks; the core's run deletes it after the period.
  First kind: `osupplier` (the DATEV import's suppliers). The office trash of copies (`office/otrash.py`) stays for the
  kinds that delete the row itself until their stage moves them.
- Never write the trash filter by hand: `live_sql(alias)` / `trash_sql(alias)` of `core/access.py`. A new
  `deleted_at IS NULL` in the server code is red in `tools/check_live_filter.py`; the existing ones stand per file in
  `tools/live_filter_baseline.json`, which only shrinks (`--update` lowers it after a clean-up).
- Write paths that do not go through `obj_write` yet (old areas during the move) use the adapters `obj_undo_pre` /
  `obj_undo_post`, `obj_history_add` and `obj_touch`.
- Stage 2 (#4711, the office and the clients): their rows have no `owner_id` / `rev` and rights of their own, so they are
  no registered kinds yet. `obj_track(kind, table, ...)` names such a kind for the history and the undo only (no rights,
  no routes, no folders); `kalmido/office/owrite.py` `ow_write(...)` is the one write call of an office row: lock, version
  (agents must send it), only the fields sent, undo step, `updated_at` / `updated_by`, history (an encrypted column stays
  sealed there), `bump`. The area checks its rights before, as it always did. `office/undo.py` keeps its route and header
  and runs on `obj_undo_run` (the steps live in `obj_undo`).
- Undo across devices, stage 1 (2.747.0, #5249): every write of a person that records a step (`obj_undo_pre`, also
  without the editor header) adds it as a part of the request's step group per account (`core/undogroups.py`,
  table `undo_groups`; the header `X-Kalmido-Undo-Group` bundles several requests within 10 seconds, `X-Kalmido-Device`
  names the device). 30 days, 300 groups per person, 256 KB per part, 2 MB or 1000 parts per group (above: listed as
  `toobig`, no copy). `core/undoweb.py`: `GET /api/undo`, `POST /api/undo/to/<id>` (newest first, the rights of now,
  a part that changed since stays and is named, a barrier stops), `POST /api/undo/<id>/redo`; `undo_barrier` for
  finalising / sending; a tracked kind registers who may take its steps back (`undo_need_reg`, the office in
  `office/undo.py`), a kind without one is never written back. People only (agents 403).
- Undo across devices, stage 4 (2.747.0, #5252): the office's step groups have area `office` and a label naming the object
  (`obj_track(undo_label=)` / `ow_kind(label=)`, `office/oubar.py`: a document by kind and number, a client or master data
  row by its name, a letter only by its object number; a sealed value never goes into a label). Finalising, sending (also
  "marked sent", a letter), a payment and its reversal, the DATEV copy and export and the period lock write a barrier
  (`oub_barrier` -> `undo_barrier`): listed, "bis hierher" stops there. `office/undogrp.py` maps every tracked office
  kind: its own check, `UGO_ADMIN` (the office's admin) or `UGO_NOACCESS` on purpose (rows with locks / approvals of
  their own). A document's undo takes the lock of its saves and of finalising (`office_doc_<id>`). The editor session
  (`X-Kalmido-Undo`) stays; in the browser a barrier ends it as an entry of the history (`office_undo.js` `oun_bar`).
- Undo across devices, stage 3 (2.774.0, #5251): diff parts (`core/undodiff.py`, `obj_undo.mode = 'diff'`): an area that
  changes its objects field by field and in masses keeps only what a step changed and takes it back through its own
  write path (`undo_diff_reg(kind, run, area)`). The tasks (`tasks/tundo.py`, kind `task`): an edit (`apply_update`, also
  batch, drag, dependent dates, a proposal applied) keeps the changed fields before / after and goes back as
  `apply_update` with `_prev` (a field changed elsewhere stays and is named, the rest goes back); completing / reopening
  keep the payload of `undo_status`; the trash, restoring and a new task go back through `trash_task` / `restore_task`.
  Sections (kind `section`: name, limits, meaning through `sec_apply`) and their order (kind `section_order`). The parts
  are read right before the commit (`Conn.pre_commit` in `core/pg.py`), so a task a batch rolled back to its savepoint
  records nothing; while a group is taken back nothing records (`undo_quiet`). Not yet: creating / deleting a section,
  the project settings, and the browser's own task history (`undo.js`), which goes once the list of stage 2 shows the
  server's groups.
- Undo across devices, stage 6 (2.777.0, #5254): calendar events (`events/evundo.py`), contacts (`contacts/ctundo.py`),
  file store nodes (`files/fsundo.py`) and habits (`personal/habitundo.py`) are tracked kinds whose write routes record a
  snap step of the person (`core/undoareas.py` `ua_pre` / `ua_post`; an event changed, moved or put into / out of the
  trash; a contact likewise; a node renamed, moved, put into / out of the trash, a new or restored version; a habit's
  settings and its trash). `obj_track(undo_free=)` lets the undo write the trash columns back; the area's fix then runs
  its own restore / trash (`ua_trash_fix`) and re-checks the target the copy puts the row into (calendar, address book,
  folder). A file's content is never copied: its step holds the version it pointed at (`cur_version`); a version the
  clean-up removed cannot come back (409); `FSU_VERSION_HOOKS` let an area refresh what it derived from the content.
  The browser's own steps (`histAdd`) stay until stages 2 / 7. Not yet: CalDAV / CardDAV and API v1 writes, budget,
  settings.
- Stage 2b (2.576.0, #4794): a 409 of `ow_write` carries the current state under `current` only (the old keys `row` /
  `letter` / `client` went). Every office row on `ow_write` has its history route `GET <its save path>/history`
  (`ow_history_answer`; e.g. `/api/office/trips/<id>/history`, `/api/clients/<id>/history`): the route runs the rights
  checks of the save route (the gate, the row in the organisation, the level "own"), and office/rights.py `ofr_need`
  asks a group for what saving needs (a "Read only" group sees the row but not its history). No state checks: the
  history of a finished row stays readable.

## 5. Routes you get

With `routes=True` (default) every kind has, without a line of its own (kalmido/core/objweb.py):

- web app: `GET/POST /api/obj/<kind>`, `GET/PATCH/DELETE /api/obj/<kind>/<id>`, `.../trash`, `.../restore`,
  `.../history`, `.../undo`, `.../shares` (+ `DELETE .../shares/<sid>`, `POST .../shares/<rid>/restore`)
- agents (API v1, MCP `list_objects` / `get_object` / `update_object`): `GET /api/v1/agent/objects/<kind>[/<id>]`,
  `PATCH /api/v1/agent/objects/<kind>/<id>` (docs/AGENTS.md *Objects of the shared core*)

The coverage guards (`tests/tenant_coverage_test.py`, `tests/freelancer_coverage_test.py`, `tests/parity_test.py`)
know these routes already (kind `obj`); an area's own extra routes need their entries as usual.

## 6. The dialog in the browser

`static/js/objsave.js` loads on demand (`await loadModule('objsave')`):

```js
objOpen(md, url, obj);                         // unsaved input comes back, undo session, version watch
const r = await saveDialog(url, obj, values);  // only the changed fields + expect_updated_at
if (r.conflict) objMerge(md, r.conflict, cur => { obj = cur; });   // fields someone else changed are marked
else obj = r;
await objUndo(url);                            // the server's undo of this dialog's own steps
```

A dialog that saves a whole form (the office's rows, the clients; 2.576.0, #4794) uses the two wrappers around it:

```js
const j = await objSaveForm(md, url, rec, body);   // saveDialog against rec (md._objBase after a conflict); null = nothing changed
// a 409 throws {status: 409, conflict}: the dialog still open -> the merge bar on it; closed at once (optimistic) ->
// again(state) opens it on the current state with the person's changes on top, then the bar
catch (x) { if (await objConflict(md, x, state => openDialog(state))) return; ... }
```

## 7. Tests

A new area tests its kind with a suite of its own (the role matrix of tests/obj_core_test.py is the pattern: two
organisations + a private person, read-only, guest, a group, an agent, an expired share, the trash) and carries the markers
`tenant-matrix:` / `freelancer-matrix:` of its routes. The core itself is tested with the test kind `objprobe`
(`KALMIDO_TEST_OBJ=1`, tests/obj_probe.py).

## Stage 3: calendars and address books (2.566.0, #4712)

- `evcal` (ev_cals, events/evkern.py) and `address_book` (books, contacts/ctkern.py) are kinds without the generic routes
  (`routes=False`); their own routes, the API v1 and CalDAV / CardDAV call the core. Their role is `obj_role`
  (events/model.py `ev_role`; the books' `book_role` reads the same share through its folder way, `ctf_node_role`).
- Their shares are rows of `fs_shares` on the object's reference node. The trigger `kalmido_kern_mirror`
  (core/migrations.d/4712_a.py) mirrors every change of the old member tables `ev_cal_members` / `book_members` into them
  (a row added, its role changed, deleted -- any code path), once the object has a node: the start's one-shot
  (`migr_kern4712`) gave every calendar / book with members its node, a new member gets it first. With a live node only the
  core's share counts, so a share taken back in the core (the file store's dialog, `obj_revoke_person`) stays taken back;
  without one the old row is still read. Stage 7 removes the old tables and the trigger.
- The way back (2.647.0, #5046): the trigger `kalmido_kern_back` (core/migrations.d/5046_a.py) on `fs_shares` deletes the
  old member row when a person's / agent's share of the node is deleted in the core (unless another live share of theirs
  stays) and gives it the core's role when that changes; it writes with `app.kern_sync`, so the mirror does not run back. An
  expiry is no event of the database: everything that asks who is a member besides the rights reads the core's live shares
  (`cal_members(..., live=True)` / `ev_member_role`, `book_members_of(..., live=True)` / `bk_member_role`): reminders, the
  heir of a deleted account, news, the agent's workspace check, the client contact link. The organisation export writes
  `members.json` only for people with a live share on the node, and the import drops an archive's member row whose node in
  the archive has no live share of that person.
- The node is the truth as soon as it exists (review of 2.566.0): a node made by any path (the first member, a share in the
  core, filing it in a folder) mirrors all member rows the object has at that moment; a node in the file store's trash is
  still the node (no share counts then, the old rows are not read again), and while it carries shares it does not go there
  on its own (the file store's protect hook), only with the object; a node removed for good first writes its shares to people
  and agents back into the member rows (trigger `kalmido_kern_node_gone`). An object that becomes private (its owner leaves
  without an heir, the organisation retires) keeps its node: it follows into the owner's private tree
  (`accounts/orgretain.py obj_nodes_follow`). A workspace move checks the node's shares (`accounts/orgs.py obj_org_set`): a
  person or agent who does not fit the new workspace, or a group's share, is a 409.
- The calendar's settings are written by `obj_write`, the calendar goes into the core's trash with its events
  (`ev_cal_trash`, restore `POST /api/evcals/<id>/restore`, purged with the events' trash run). Events are no kind of their
  own (their series, attendees and iCalendar have rules of their own): every change runs under the series lock
  `write_lock('obj-event-<id>')` with the row read again (`ev_lock`), CalDAV's If-Match under the same lock.

## Agents' changes as a proposal (2.623.0, #4718)

`POST /api/v1/agent/objects/<kind>/<id>/proposals` `{values, expect_updated_at, summary?, user_id?}` (agents/objprop.py,
MCP `propose_object_change`) is the agent's second way next to the direct `PATCH`: no own write path, the proposal is a
job of kind `obj_patch` of agents/proposals.py, and accepting it is `obj_write`.
- Proposing: `obj_need(agent, 'view')` (only what the agent sees: its workspace, the data lock, `hidden`; a view share is
  enough), the token needs the kind's read scope (`_agent_kind`) and is not read-only (api/scopes.py `AGENT_RO_REFUSED`). The values go through the kind's cleaners against the row
  (`_clean`: unknown field / bad value 400), `expect_updated_at` is required (400 `version_required`) and must be the current
  version (`ccf_check`, 409 with the current state); nothing would change = 400. At most 100 per agent and day.
- The card goes to `user_id` (a person with `edit` / `manage` on the object, `obj_role`) or to the object's owner (the same
  check); only that person opens, accepts and discards it (`need_prop`). The proposal stores the raw values, the cleaned
  ones and the values before, and the version the agent read.
- Accepting: `obj_write(person, kind, id, values, expect=version)` -- the person's write right, the write lock, the version
  check (a change by anybody since: 409 with a plain message, nothing written), the history names the person. Undo / redo of
  the proposal write the values back with the version the last step left (changed since: skipped).
- Old areas: nothing moves yet (stage 2: office and clients #4711, stage 3: calendars and contacts #4712).
- Stage 5 (#4719, 2.565.0): team chat channels and group conversations are the kind `tchat_room` (collab/tcxcore.py,
  listed=False); members are shares (person, agent, group), tchat_members stays the reader fallback (kept in step at every
  start, tcx_core_sync) until stage 7. The materialisation of group shares into list_members.grole stays until stage 6 (#4739).
- Stage 6 (2.568.0, #4739): the projects' shares (members, the project's agent) are share rows of the core on the project's
  node (expiry, created_by, taken back into `obj_revoked`, restorable: `GET /api/lists/<id>/shares`,

## Stage 4: tables and knowledge pages (2.565.0, #4717)

Tables and knowledge pages keep the reference kinds of the file store they had (`sheet`, `wiki`; they are not `obj_register`ed),
but their shares with people and agents are core shares now: rows of `fs_shares` on the table's / page's / folder's reference
node, written and taken back with `obj_node_share` / `obj_node_unshare` (core/objects.py: the share row, `obj_revoked`, the
log; the area checks who may share and with whom first, as `obj_share` does with `obj_need`). A table in no folder gets its
node at the top of its workspace's tree (sheets/shshare.py `shs_node`); taking a table out of a folder keeps its node with its
own shares (files/fsref.py `fs_ref_place`). A share of a knowledge folder is a share of the folder's node (and of the page of
the same name), no longer a path prefix, so it follows renames, moves and a restore as "Name (2)".

The old rows (`sheet_shares`, `wiki_shares` kind person) stay as the share's card (the dialog's id, an address typed in, the
switch "show pictures") with `core_id` (+ `core_id2`) and give nothing themselves; a row not moved yet (`core_id` NULL) is
read as before for one release (core first, then the old row). The one-shot `migr_core4717` (core/db.py) and the areas
(`shs_core_move`, `wsh_core_move`) copy them forward. Public links of pages stay rows of `wiki_shares` (no share with an
account). Not moved yet: the tables' and pages' own fields (title, name) still save through their areas, not `obj_write`.

## Stage 6b: the side objects of a project (2.610.0, #4762)

Custom field options, the people of a task, waiting on, templates, comments, a sprint's dialog and the trash of sections,
planned sprints and templates write through `kalmido/core/objparts.py` instead of the pieces each route had since 2.564
(#4701, versions) and 2.567 (#4707, trash). Like the office's rows they have no `owner_id` / `rev` and the project's rights,
so they are no registered kinds: `part_kind(kind, table, lock=..., version=..., key=..., agent=...)` names one (its lock
keeps the name the area's other writes use, e.g. `task-<id>` of `apply_update`, `sprints:<list>` of start / close).
- `part_write(c, kind, id, body, apply)`: the lock, the row again under it (gone = 404), the area's own check of what the
  client saw (`check`: a field's option list), the version check (`expect_updated_at` -> 409 with the current state under
  the kind's key, `template` / `comment` / `sprint` as before), then the area's writer. The caller bumps and commits.
- `part_merge(have, seen, mine)`: a list sent whole against `_prev` (a person another device added stays).
- `part_trash` / `part_restore` for rows with `deleted_at` (templates); `part_copy` / `part_copy_take` / `part_copy_back`
  for the copy in `list_part_trash` (sections, planned sprints: restored with their id). Agents never take a section or a
  sprint back (`agent=False`).
- The routes, their answers and their rights stay as they were. No history and no undo steps of their own yet: these rows
  are deleted for good without the core knowing (a field, a comment, the trash period), an `obj_history` row would outlive
  them. A custom field's values (`set_field_values`) stay part of the task's write (`apply_update`: under the task's lock,
  compared per field against `_prev`).

## Stage Q0b: the light kinds task, event, hub_mail, client (2.754.0, #5268)

Every (kind, id) table of the core that comes next (links, tags, comments, seen, follow) needs a kind for the objects of the
old areas it points at. `kalmido/core/objlight.py` registers four kinds without a reference node
(`obj_register(..., node=False)`): `task`, `event`, `hub_mail`, `client`. Such a kind has no shares, no folder, no generic
routes, no fields and no write path of the core (`obj_reg_node` refuses it with 404 in `core/writes.py`; `obj_visible_sql` /
`obj_rows` with ValueError: the area lists its own rows). It only answers
- `obj_role` / `obj_need`: steps 1 + 2 as for every kind (organisation floor, an agent of another workspace never, an API
  token's list limit), then `base_role` = exactly the area's own check for the account asked about: a task its project role
  (`need_task`: owner / project admin `manage`, editor `edit`, viewer `view`, a participant only the tasks `pvis` shows,
  `edit` where they may write; a parent that is only context gives nothing), an event `ev_role_of` (calendar owner `manage`,
  an invited person `view`), a filed e-mail `hbm_can` in the app (write = `edit`) and the API v1 rule `hmv_can` for agents
  and tokens (read only, never "Not assigned"), a client `need_client` (`edit` unless read-only in its organisation,
  `manage` for who may delete it). Agents get nothing the area does not give them.
- `obj_title` (live, never stored; a task of an end-to-end locked project has none), `open_url` (`t/<id>`, `ev/<id>`,
  `mailhub/<id>`, `client/<id>`) and `obj_space`.
Nothing of the areas moved: their routes, rights and tables stay as they are. Test containers have
`GET /api/test/objrole/<kind>/<id>` (tests/p2754_d_kinds_api_test.py).

## Cross-cutting parts (2.755.0, #5267)

Links between objects, tags, comments, reactions, read marks, versions and following / notifying exist **once**, in the
shared core (the stages Q1-Q9 of the cross-cutting analysis move them there one by one: reactions `obj_reactions`, links
`obj_links`, comments, tags, the shared search, versions, read marks, `obj_follow`). A new area builds none of them itself.

`tools/check_core_crosscut.py` (CI lint, seconds, no database) reads schema.py and the fragments of migrations.d and is red on a
new table that looks like one of them:
- its name ends in `_links`, `_tags`, `_comments`, `_notes`, `_reactions`, `_rx`, `_trash_text`, `_reads`, `_seen`,
  `_versions`, `_hist`, `_notif`, `_watchers`, `_bell`, `_follow` or `_subscriptions`, or
- it has an `*_id` column and one of `tag`, `tag_id`, `body`, `seen_id`, `last_id`, `read_at`, `seen_at`, `emoji`, `follow`,
  `muted`, `no`, or
- it only joins two tables (two `*_id` columns with `REFERENCES` to different tables, besides them at most `id`,
  `created_at`, `created_by`, `sort`).

Not counted: the core's own tables (`obj_*`), tables with `token_hash`, `url`, `base_url` or `role` (share links, address
lists, roles), and a table a fragment drops (`DROP TABLE IF EXISTS` in AFTER). In the code outside `kalmido/core/` a new
`MENTION_RE`, `need_*_say(` or `*_react(` is red, a new `*_search(` a hint.

What is there today stands in `tools/core_crosscut_allow.json` with its reason: the stage that takes it down, or the area's own
logic (a task's placement in lists, a mail's text, an IMAP de-duplication ...). The list grows only with a decision of the product owner.
A stage that takes a table or a function down takes its line out in the same commit; a line whose table or function is gone is
red.

### Reactions (stage Q1, 2.763.0, #5269)

One table `obj_reactions(target_kind, target_id, user_id, emoji, created_at TIMESTAMPTZ)` holds every reaction; it replaced
`comment_reactions`, `tchat_rx` and `chat_reactions`. Target kinds: `comment` (comments of tasks), `tchat` (team chat
messages), `agent_chat` (the chat with an agent). `kalmido/core/objreact.py`:
- `orx_toggle(c, kind, id, uid, emoji, on, own=, say=)`: the one rule -- not on one's own message (400, taking an old one back
  works) and not for who may only read (`say`: the area's hook returning the organisation's refusal text,
  `accounts/orgroles.py org_say_refusal`; 403; taking one back stays). `on=None` toggles.
- `orx_set` writes it, `orx_of` reads `{id: [{emoji, count, users}]}` (emojis in the order of their first use).
- What a reaction means on top (an approval, a suggestion applied, an agent's event) stays in the area
  (`collab/reactions.py react`, `agents/chat.py chat_react`).

The target has no foreign key; the trigger `kalmido_orx_gone` deletes a target's reactions when its row is deleted for good.
A comment or team chat message in the trash keeps them (it shows none), a restore brings them back. The organisation export
writes them into the old files (`comments/reactions.json` with `comment_id`, `chat/reactions.json` with `message_id`), so
older archives and new ones import the same way. A new area with reactions adds its kind to `ORX_KINDS` and a trigger line in
a fragment -- no table of its own.
