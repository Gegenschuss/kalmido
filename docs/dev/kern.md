# The shared core: how to build a new area

*Since 2.558.0 (stage 1). For developers of Kalmido.*

A new area (meetings, a social media planner, team projects ...) needs **no share table of its own, no check function of
its own and no save path of its own**. It registers its kind of object with the core and uses three calls:

1. `obj_register(...)` once at import (kalmido/core/objects.py)
2. `obj_need(c, uid, kind, id, "view" | "write" | "manage")` in every route that reads or changes an object
3. `obj_write(c, uid, kind, id, body)` to change it (kalmido/core/writes.py)

The rest comes with the core: shares to people, groups and agents (with expiry, through folders of the file store too),
the organisation roles, the version check against lost updates, the history, undo, the trash, the change counter that
tells the other devices, generic routes for the web app and for agents, and a small client for dialogs
(static/js/objsave.js). Old areas move onto the core step by step (stage 2: office and clients, stage 3: calendars and
contacts); stage 1 changes none of them.

## 1. The table

A fragment `kalmido/core/migrations.d/<task>_<x>.py` creates the area's table with at least these columns (names fixed):

```sql
CREATE TABLE IF NOT EXISTS meetings (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  org_id BIGINT REFERENCES orgs(id) ON DELETE CASCADE,          -- NULL = private
  owner_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- private ones go with the account; the core hands an
                                                                -- organisation's to the heir first
  rev BIGINT NOT NULL DEFAULT 1, created_at TEXT NOT NULL, created_by BIGINT,
  updated_at TEXT NOT NULL, updated_by BIGINT, deleted_at TEXT, deleted_by BIGINT,
  title TEXT NOT NULL DEFAULT '', agenda TEXT NOT NULL DEFAULT '', starts DATE);
CREATE INDEX IF NOT EXISTS meetings_trash ON meetings(deleted_at) WHERE deleted_at IS NOT NULL;  -- the trash list
```

Add the table to `kalmido/core/rls.py` TABLES (it has an `org_id`) and to the export lists (`tools/check_export_tables.py`
says where). The core keeps its own data in `obj_history`, `obj_undo` and `obj_revoked`; shares are rows of `fs_shares`
on the object's reference node in the file store.

## 2. Register the kind

```python
from ..core.objects import f_date, f_text, obj_register
from ..core.i18n import N_

obj_register("meeting", "meetings", label=N_("Meeting"), area="calendar",
             fields={"title": f_text(200, required=True), "agenda": f_text(20000, line=False), "starts": f_date()},
             scopes=("calendar", "calendar"), open_url=lambda rid: f"meetings/{int(rid)}")
```

- `fields`: what may be set, each with its cleaner `f(c, value, row) -> clean value` (raise `BadInput`); `None` = the field
  was not sent at creation (its default). Helpers: `f_text`, `f_int`, `f_bool`, `f_choice`, `f_date`.
- `area`: the change counter of `/api/version` (`core/db.py` LV_AREA_KEYS); the other devices reload that area.
- `org_access`: what a full member of the organisation gets without a share: `"edit"` (default), `"view"` or `None`
  (only the owner, the admins and explicit shares).
- `scopes`: the read / write scope an agent's token needs on the agent routes.
- `routes=False` when the area brings its own routes only (then it calls the same functions).
- Hooks for areas with rules of their own (stage 2 / 3): `base_role` (+ its `visible` SQL), `space`, `cap`, `hidden`,
  `dl_area` (an agent's data lock), `undo_scope` (more tables than the main row), `public`, `protect`, `on_trash`, `content`.

The kind is registered with the file store's reference nodes at the same time (files/fsref.py): the object can lie in
folders, and a folder share opens it.

## 3. Who may do what

`obj_role(c, uid, kind, id)` is the one role: `None` < `view` < `edit` < `manage`.

| Who | Private object | Organisation's object |
|---|---|---|
| Its owner | manage | manage (member), view (read-only / guest / accounting now) |
| Organisation admin | - | manage |
| Member | - | `org_access` (edit by default) |
| Read-only member | - | view |
| Guest, accounting | - | only a personal share |
| A share (person, group, agent; folder above too) | view / edit | view / edit (read-only members at most view) |
| An agent | only a share | only a share, only of its own workspace |

On top: another organisation never (404), what `hidden` names never opens through a share (agents and tokens: not even
through the area's own role), an agent's data lock, a token limited to lists, and the trash (only `manage` sees an object
there). `obj_need` turns this into 404 / 403; `obj_visible_sql(c, uid, kind)` / `obj_rows(...)` give the lists. A kind
with a `cap` hook lists only with `obj_rows` (it asks `obj_role` per row): `obj_visible_sql` refuses it with `ValueError`,
because a share there may open less than the SQL would name.

Losing access is in one place too: `obj_revoke_person(c, uid, org, reason)` runs when a person leaves an organisation
(their and their agents' shares on its nodes, their team chat rooms there; their objects go to the heir), when a role
goes down to guest / accounting (the open channels they joined), when an organisation retires (every share on its nodes,
every room membership) and when an account is deleted (its organisation objects go to the heir, `upg_heir`, before the
account and its `owner_id` cascade; its private ones go with it; when other people are left but no admin or member who may take them,
the deletion is refused as for calendars, `upg_heirless`). What goes waits 30 days in `obj_revoked`; a manager can put a
share back (`obj_share_restore`). Retiring an organisation takes every share of the file store on its nodes for good:
there is no way back out of the retirement, so after the 30 days those rows are gone (its export has no shares then).

## 4. Saving

```python
row, changed = obj_write(c, uid, "meeting", mid, body())   # rights, lock, version, fields, history, undo, bump
c.commit()
```

- Only the fields sent change; an unknown field is 400.
- `expect_updated_at` in the body = the `updated_at` the client read: another one -> 409 with the current state under
  `current`, nothing written. People may leave it out (old clients); **agents must send it** (400 without).
- Each change: `rev+1`, `updated_at`, `updated_by`, an entry in the history (one person's changes within ten minutes
  merge; an agent's are marked), the title on the reference node, `bump` of the area.
- `obj_create`, `obj_trash`, `obj_restore`, `obj_purge` (only from the trash), `obj_history`, `obj_undo`. `obj_trash` puts the
  object's reference node into the file store's trash with it and `obj_restore` brings that node back, so the folders and
  their searches hide a trashed object like any node in the trash (no extra clause per kind). Should the file store's
  trash empty the node first, the object comes back without its folder place.
- Write paths that do not go through `obj_write` yet (old areas during the move) use the adapters `obj_undo_pre` /
  `obj_undo_post`, `obj_history_add` and `obj_touch`.

## 5. Routes you get

With `routes=True` (default) every kind has, without a line of its own (kalmido/core/objweb.py):

- web app: `GET/POST /api/obj/<kind>`, `GET/PATCH/DELETE /api/obj/<kind>/<id>`, `.../trash`, `.../restore`,
  `.../history`, `.../undo`, `.../shares` (+ `DELETE .../shares/<sid>`, `POST .../shares/<rid>/restore`)
- agents (API v1, MCP `list_objects` / `get_object` / `update_object`): `GET /api/v1/agent/objects/<kind>[/<id>]`,
  `PATCH /api/v1/agent/objects/<kind>/<id>` (docs/AGENTS.md *Objects of the shared core*)

The coverage guards (`tests/tenant_coverage_test.py`, `tests/freelancer_coverage_test.py`, `tests/parity_test.py`)
know these routes already (kind `obj`); an area's own extra routes need their entries as usual.

## 6. The dialog in the browser

`static/js/objsave.js` loads on demand (`await loadModule('objsave')`):

```js
objOpen(md, url, obj);                         // unsaved input comes back, undo session, version watch
const r = await saveDialog(url, obj, values);  // only the changed fields + expect_updated_at
if (r.conflict) objMerge(md, r.conflict, cur => { obj = cur; });   // fields someone else changed are marked
else obj = r;
await objUndo(url);                            // the server's undo of this dialog's own steps
```

## 7. Tests

A new area tests its kind with a suite of its own (the role matrix of tests/obj_core_test.py is the pattern: two
organisations + a private person, read-only, guest, a group, an agent, an expired share, the trash) and carries the markers
`tenant-matrix:` / `freelancer-matrix:` of its routes. The core itself is tested with the test kind `objprobe`
(`KALMIDO_TEST_OBJ=1`, tests/obj_probe.py).

## Not in stage 1

- Agents' changes as a proposal a person accepts (proposal kind `obj_patch`): the first area that needs it adds it
  (agents/proposals.py); stage 1 has the direct write with the version.
- Old areas: nothing moves yet (stage 2: office and clients #4711, stage 3: calendars and contacts #4712).
