# The shared core: how to build a new area

*Since 2.558.0 (stage 1). For developers of Kalmido.*

A new area (meetings, a social media planner, team projects ...) needs **no share table of its own, no check function of
its own and no save path of its own**. It registers its kind of object with the core and uses three calls:

1. `obj_register(...)` once at import (kalmido/core/objects.py)
2. `obj_need(c, uid, kind, id, "view" | "write" | "manage")` in every route that reads or changes an object
3. `obj_write(c, uid, kind, id, body)` to change it (kalmido/core/writes.py)

The rest comes with the core: shares to people, groups and agents (with expiry, through folders of the file store too),
the organisation roles, the version check against lost updates, the history, undo, the trash, the change counter that
tells the other devices, generic routes for the web app and for agents, and a small client for dialogs
(static/js/objsave.js). Old areas move onto the core step by step (stage 2: office and clients, stage 3: calendars and
contacts); stage 1 changes none of them.

## 1. The table

A fragment `kalmido/core/migrations.d/<task>_<x>.py` creates the area's table with at least these columns (names fixed):

```sql
CREATE TABLE IF NOT EXISTS meetings (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  org_id BIGINT REFERENCES orgs(id) ON DELETE CASCADE,          -- NULL = private
  owner_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- private ones go with the account; the core hands an
                                                                -- organisation's to the heir first
  rev BIGINT NOT NULL DEFAULT 1, created_at TIMESTAMPTZ NOT NULL, created_by BIGINT,
  updated_at TIMESTAMPTZ NOT NULL, updated_by BIGINT, deleted_at TIMESTAMPTZ, deleted_by BIGINT,
  title TEXT NOT NULL DEFAULT '', agenda TEXT NOT NULL DEFAULT '', starts DATE);
CREATE INDEX IF NOT EXISTS meetings_trash ON meetings(deleted_at) WHERE deleted_at IS NOT NULL;  -- the trash list
```

Points in time are `TIMESTAMPTZ` (2.760.0, #5311; new tables take real types, checked by the column type lint of #5305). The app
reads them as ISO text in one canonical form (`kalmido/core/pg.py` `ts_canon`: UTC, `+00:00`, microseconds only when there
are any), the same form the older `TEXT` columns hold, and writes the ISO text of `now_iso()` as before. So the answers,
the history, undo and the version check (`expect_updated_at`, `ccf_check` compares both sides canonically) behave alike for
`TEXT` and `TIMESTAMPTZ` tables; an older area moves its columns over in its stage. Never compare such a column with `''`
(`deleted_at IS NULL` / `IS NOT NULL`), and a trigger never takes one as `to_jsonb(row)->>'..._at'` (that text carries the
session's zone, not the canonical form): use `to_char(x AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"+00:00"')`.

Add the table to `kalmido/core/rls.py` TABLES (it has an `org_id`) and to the export lists (`tools/check_export_tables.py`
says where). The core keeps its own data in `obj_history`, `obj_undo` and `obj_revoked`; shares are rows of `fs_shares`
on the object's reference node in the file store.

## 2. Register the kind

```python
from ..core.objects import f_date, f_text, obj_register
from ..core.i18n import N_

obj_register("meeting", "meetings", label=N_("Meeting"), area="calendar",
             fields={"title": f_text(200, required=True), "agenda": f_text(20000, line=False), "starts": f_date()},
             scopes=("calendar", "calendar"), open_url=lambda rid: f"meetings/{int(rid)}")
```

- `fields`: what may be set, each with its cleaner `f(c, value, row) -> clean value` (raise `BadInput`); `None` = the field
  was not sent at creation (its default). Helpers: `f_text`, `f_int`, `f_bool`, `f_choice`, `f_date`.
- `area`: the change counter of `/api/version` (`core/db.py` LV_AREA_KEYS); the other devices reload that area.
- `org_access`: what a full member of the organisation gets without a share: `"edit"` (default), `"view"` or `None`
  (only the owner, the admins and explicit shares).
- `scopes`: the read / write scope an agent's token needs on the agent routes.
- `routes=False` when the area brings its own routes only (then it calls the same functions).
- Hooks for areas with rules of their own (stage 2 / 3): `base_role` (+ its `visible` SQL), `space`, `cap`, `hidden`,
  `dl_area` (an agent's data lock), `undo_scope` (more tables than the main row), `public`, `protect`, `on_trash`, `content`.
- An old area that keeps its own role table and reference kind (stage 6, the projects, `kalmido/lists/lmcore.py`):
  `fsref=False` (the area's registration in files/fsref.py stays; the shares of its node are already in its base role, so
  `obj_role` does not read them again), `share_cols` (its own columns on `fs_shares`, e.g. `list_role` / `list_own`, put back
  by `obj_share_restore`), `on_restore` (the area puts its role table right under its own rules after a restore, or refuses;
  only for the area's own rows of a person / an agent, `list_own = 1` -- any other row of the node takes the core's way, a
  group's own row is refused with 409), the reason `expired` in `obj_revoked` for an own row that ran out,
  `on_revoke` (its part of `obj_revoke_person`) and `list_col` (the column a token's project limit is checked against). Its
  routes call `obj_share(..., extra=..., checked=True)` / `obj_unshare(..., checked=True)` after checking the right and the
  target themselves.
- An area whose own sharing dialog writes the shares of the object's node (stage 3, the calendars and address books):
  `node_shares=True` (2.924.0, #5069; with `on_share_back=f(c, uid, id, share)` for the dialog's side effects when a share
  comes back through the core's restore; it replaced `members=(table, key column)`, the old member table, gone since stage 7b):
  the node stays out of the file store's trash alone while it carries shares, the shares of the owner's own agents stay when
  the organisation retires, and the generic routes `GET /api/obj/<kind>/<id>/shares` + `POST .../shares/<rid>/restore` work
  for the kind (the shares taken back, restorable 30 days). The dialog writes with `obj_node_person_put(c, by, node, target,
  role)` / `obj_node_person_drop(c, kind, id, target)` after its own checks. `fs_hooks={...}` replaces keyword arguments of the file store's registration, for a kind the file store knew before the core
  (the address books keep their folder rules: filing and sharing the node stay with who manages it).

The kind is registered with the file store's reference nodes at the same time (files/fsref.py): the object can lie in
folders, and a folder share opens it.

`listed=False` (2.565.0, #4719, the team chat's rooms): the reference node only carries the object's shares. It lies in no
folder, the file store never lists, searches or opens it (fs_ref_rows, fs_ref_hidden_sql, need_node) and it is never filed
(409). The area writes its members with `obj_member_put(c, by, kind, id, key, target, role)` / `obj_member_take(c, by, kind,
id, key, targets, reason)` after its own rule decided (no pool check of the file store: a group conversation spans
workspaces); taken shares land in `obj_revoked`. `obj_share_rows_sql(kind)` reads the live shares in bulk, `obj_gate(c, uid,
kind, row)` is the core's floor for a row the area listed itself (`obj_token_lists(uid)` its token part). With a `cap` hook that gives nothing, the area's base role
is the only role and reads the shares itself (collab/tcxcore.py).

## 3. Who may do what

`obj_role(c, uid, kind, id)` is the one role: `None` < `view` < `edit` < `manage`.

| Who | Private object | Organisation's object |
|---|---|---|
| Its owner | manage | manage (member), view (read-only / guest / accounting now) |
| Organisation admin | - | manage |
| Member | - | `org_access` (edit by default) |
| Read-only member | - | view |
| Guest, accounting | - | only a personal share |
| A share (person, group, agent; folder above too) | view / edit | view / edit (read-only members at most view) |
| An agent | only a share | only a share, only of its own workspace |

On top: another organisation never (404), what `hidden` names never opens through a share (agents and tokens: not even
through the area's own role), an agent's data lock, a token limited to lists, and the trash (only `manage` sees an object
there). `obj_need` turns this into 404 / 403; `obj_visible_sql(c, uid, kind)` / `obj_rows(...)` give the lists. A kind
with a `cap` hook lists only with `obj_rows` (it asks `obj_role` per row): `obj_visible_sql` refuses it with `ValueError`,
because a share there may open less than the SQL would name.

Office documents filed in a folder (`office/docref.py`, decision of #2742, confirmed with #5048): the folder share and the
office groups are two ways in, and the higher one counts for the document itself -- a folder share can lift reading or
changing a draft above the person's office group in the area (also for a member whose group gives the area nothing). The
cap stays the organisation role only (`ofd_cap`: guests nothing, read-only / accounting read). Everything beyond the
document stays with the office groups: finalising, releasing / sending, payments, locking periods, exports and deleting
have no route on the folder way (`/api/fsref/office_doc/<id>`: read, PDF, head fields without status / number / links into
the master data, positions), and a finalised document stays unchangeable (409). Agents only through a share with exactly
them, and then read only.

Losing access is in one place too: `obj_revoke_person(c, uid, org, reason)` (called by the layer accounts through
`core/objhooks.person_revoked`, so accounts never imports the core's modules; `core/objects.py` and `core/writes.py`
belong to the layer domain, `core/objweb.py` to the layer integrations, `LAYER_OF` in `kalmido/__init__.py`) runs when a person leaves an organisation
(their and their agents' shares on its nodes, their team chat rooms there; their objects go to the heir), when a role
goes down to guest / accounting (the open channels they joined), when an organisation retires (every share on its nodes,
every room membership) and when an account is deleted (its organisation objects go to the heir, `upg_heir`, before the
account and its `owner_id` cascade; its private ones go with it; when other people are left but no admin or member who may take them,
the deletion is refused as for calendars, `upg_heirless`). What goes waits 30 days in `obj_revoked`; a manager can put a
share back (`obj_share_restore`). Retiring an organisation takes every share of the file store on its nodes for good:
there is no way back out of the retirement, so after the 30 days those rows are gone (its export has no shares then).

## 4. Saving

```python
row, changed = obj_write(c, uid, "meeting", mid, body())   # rights, lock, version, fields, history, undo, bump
c.commit()
```

- Only the fields sent change; an unknown field is 400.
- `expect_updated_at` in the body = the `updated_at` the client read: another one -> 409 with the current state under
  `current`, nothing written. People may leave it out (old clients); **agents must send it** (400 without).
- Each change: `rev+1`, `updated_at`, `updated_by`, an entry in the history (one person's changes within ten minutes
  merge; an agent's are marked), the title on the reference node, `bump` of the area.
- `obj_space_set(c, uid, kind, id, org_id)` (2.579.0, #4802): the object moves into an organisation or back into its owner's
  own space -- e.g. a saved view an admin shares with everyone of the organisation (members then get the kind's `org_access`).
  'manage', a person; into an organisation as for `obj_create`; out of one only its admin (logged, `accounts/orgout.py`); refused
  (409) while its node carries shares. Register a kind with `org_join="admin"` when only admins may bring its objects into an
  organisation (at creation too): a member's objects of it stay private.
- `obj_create`, `obj_trash`, `obj_restore`, `obj_purge` (only from the trash), `obj_history`, `obj_undo`. `obj_trash` puts the
  object's reference node into the file store's trash with it and `obj_restore` brings that node back, so the folders and
  their searches hide a trashed object like any node in the trash (no extra clause per kind). Should the file store's
  trash empty the node first, the object comes back without its folder place.
- 2.773.0 (#5292): this is THE trash of the core. `children=((table, key column), ...)` in `obj_register` = rows of other
  tables that belong to the object: they go into the trash with it (its `deleted_at`), come back with it (only the ones that
  went with it) and are deleted for good with it. A trash / restore of a person is a step of the list of steps
  (`GET /api/undo`, mode `trash` / `restore`, no copy): taking it back runs `obj_restore` / `obj_trash` with the rights of
  now. `trash_prune=True` lets the core's retention run (`obj_trash_tick`, hourly, `ret_trash_cut` + the switch "trash")
  delete the kind's trash the same way as `obj_purge`; an area with its own run keeps it until its stage moves it.
- 2.784.0 (#5366, stage 4): an office kind that deletes by `deleted_at` registers with `office/okern.py ofk_register(kind,
  table, label, rights area, need)` (no routes, node or listing; the core's role = the office's level `need` in that area)
  and its own routes call `ofk_trash` / `ofk_restore` after their office checks; the core's run deletes it after the period.
  First kind: `osupplier` (the DATEV import's suppliers). The office trash of copies (`office/otrash.py`) stays for the
  kinds that delete the row itself until their stage moves them.
- 2.783.0 (#5368, stage 6): the side objects (`core/objparts.py`, no registered kinds: their rights are the project's) use
  the same run. `part_kind(..., trash_prune=True)` hands their trash to `obj_trash_tick` / `obj_trash_prune`: rows with
  `deleted_at` (inbound webhooks `hook_in`, the team chat's tombstones `tchat_msgs` with the thread rule as `prune` and their
  files through `on_prune`, unlinked after the commit, the member memos) or, with `copy=True`, their copies in
  `list_part_trash` (sections, planned sprints, deleted custom fields, the Undo copies of "Delete all times"). The webhooks
  go into the trash and back with `part_trash` / `part_restore`, a deleted field with `part_copy` / `part_copy_back`. The old
  tables `field_trash` and `time_wipes` stay for the version before; their rows move into `list_part_trash` at every start
  (`ftr_move`, `tzw_move`: one-way for those rows). No own runs any more in `files/trashpurge.py` or `integrations/hookin.py`
  for these kinds.
- 2.809.0 (#5365, stage 3 of the trash): `obj_on_purge(kind, f)` = the area's part of the delete for good: `f(c, id)` runs
  first in `_purge_rows` (in a savepoint), cleans what the core does not know (stored files, scan / text rows, folder nodes)
  and returns the work for after the commit (paths or callables); `Denied` keeps the object (a receipt under the legal
  retention): `obj_purge` refuses, the retention run counts it as `<kind>_locked` and leaves it in the trash. Purges that
  may meet such a hook run inside `obj_purge_after()` and call `unlink_files(box["after"])` after their commit

  (`wiki/wkkern.py`, `wiki_page`, children `wiki_files`) and tables (`sheets/shkern.py`, `sheet_table`) are core kinds
  without routes, node or listing: their routes check the area's rights, then call `obj_trash` / `obj_restore` / `obj_purge`
  (no core step: the areas keep their own undo); `base_role` mirrors the area's rule of deleting / restoring, the space hook
  names no organisation (the area's rule checks it). Their own purge runs (`tp_files`, `wiki_trash_tick`, the tables' line
  of `tp_tick`, `wiki_purge`, `shx_purge`) are gone. Not yet on the core: files trashed on their own (knowledge files

## 5. Routes you get

With `routes=True` (default) every kind has, without a line of its own (kalmido/core/objweb.py):

- web app: `GET/POST /api/obj/<kind>`, `GET/PATCH/DELETE /api/obj/<kind>/<id>`, `.../trash`, `.../restore`,
  `.../history`, `.../undo`, `.../shares` (+ `DELETE .../shares/<sid>`, `POST .../shares/<rid>/restore`)
- agents (API v1, MCP `list_objects` / `get_object` / `update_object`): `GET /api/v1/agent/objects/<kind>[/<id>]`,
  `PATCH /api/v1/agent/objects/<kind>/<id>` (docs/AGENTS.md *Objects of the shared core*)

The coverage guards (`tests/tenant_coverage_test.py`, `tests/freelancer_coverage_test.py`, `tests/parity_test.py`)
know these routes already (kind `obj`); an area's own extra routes need their entries as usual.

## 6. The dialog in the browser

`static/js/objsave.js` loads on demand (`await loadModule('objsave')`):

```js
objOpen(md, url, obj);                         // unsaved input comes back, version watch
const r = await saveDialog(url, obj, values);  // only the changed fields + expect_updated_at
if (r.conflict) objMerge(md, r.conflict, cur => { obj = cur; });   // fields someone else changed are marked
else obj = r;
```

A dialog that saves a whole form (the office's rows, the clients; 2.576.0, #4794) uses the two wrappers around it:

```js
const j = await objSaveForm(md, url, rec, body);   // saveDialog against rec (md._objBase after a conflict); null = nothing changed
// a 409 throws {status: 409, conflict}: the dialog still open -> the merge bar on it; closed at once (optimistic) ->
// again(state) opens it on the current state with the person's changes on top, then the bar
catch (x) { if (await objConflict(md, x, state => openDialog(state))) return; ... }
```

## Cross-cutting parts (2.755.0, #5267)

`tools/check_core_crosscut.py` (CI lint, seconds, no database) reads schema.py and the fragments of migrations.d and is red on a

- its name ends in `_links`, `_tags`, `_comments`, `_notes`, `_reactions`, `_rx`, `_trash_text`, `_reads`, `_seen`,

- it only joins two tables (two `*_id` columns with `REFERENCES` to different tables, besides them at most `id`,
  `created_at`, `created_by`, `sort`).

Not counted: the core's own tables (`obj_*`), tables with `token_hash`, `url`, `base_url` or `role` (share links, address
lists, roles), and a table a fragment drops (`DROP TABLE IF EXISTS` in AFTER). In the code outside `kalmido/core/` a new
`MENTION_RE`, `need_*_say(` or `*_react(` is red, a new `*_search(` a hint.

Shares and rights checks (2.846.0, #5522): who may do what exists once too (section 3). The same check is red on
- a new table whose name ends in `_shares`, or that holds an `*_id` on users, organisations, groups or agents (`user_id`,
  `org_id`, `group_id`, `agent_id`, `owner_id`, or `REFERENCES` one of these tables) together with a `role` or `perm*` column
  (also one added later with `ALTER TABLE ... ADD COLUMN`) -- here `role` and the other exceptions above do not count;
- a new `def need_*(`, `def *_role(` or `def *_can(` outside `kalmido/core/`: a rights check of its own. A new area asks

  filter, `kflt_rows(host, conds, cat, {changed, addBtn})` only the condition rows (for a dialog of the area's own)
- server: `kalmido/core/filters.py` -- `kflt_where(rules, cond, old)` -> one SQL condition, `kflt_match(item, rules, cond, old)`,
  `kflt_cond(cnd, has, empty)` for value lists

The guard (2.857.0, #5523): `tools/check_core_crosscut.py` (CI) turns red on a filter evaluator or a condition dialog of its
own outside the three files above -- Python `def *filter_sql / *filter_where / *filter_match / *filter_rules / *filter_cond(s)
/ *_cond_ok / *_match_rule(s) / *_filters(`, browser `*filterMatch / *Cond(s) / *_cond(s) / *CondOk / *FilterDlg /
*FilterDialog / *CondDlg / *CondRows / *FilterRows` -- unless it only uses the core (its block calls `kflt_*`, or it is named in
such a block or in a catalog as `cond` / `old`). Today's others (search bars, automation triggers, id maps) stand with their
reason in `tools/core_crosscut_allow.json` section `filter`.

The format, stored as it is (JSON):

```js
rules = {op: 'and' | 'or', conds: [{f: 'kind', op: 'in', v: ['pdf']}, {f: 'text', op: 'has', v: 'offer'}, {f: 'kind', op: 'nin', v: ['img']}]}
```

`f` is a key of the catalog, `op` the comparison: `in` / `is` (any of the values), `nin` / `isnot` (none of them; these hold
**always on top, also with OR**), `empty`, `has` / `nhas` (text), `gt` / `lt` / `eq` / `set` (numbers, the area's own `cond`).
A condition without values or with an empty text is off. An older stored form of the area converts through `old`; the
stored data stays as it is (the lists' old rules, the segments' `{tags, companies, books, not_*}`).

The catalog:

```js
const DOC_FLT = {
  has: {kind: (d, x) => d.kind === x, folder: (d, x) => d.folder === x},  // the item has this one value
  empty: {folder: ''},                        // what "is empty" stands for (only these)
  text: d => [d.title, d.note],               // f 'text': contains (any of them)
  // cond: c => test | null | undefined       // own kinds (numbers, custom fields); undefined = the core's
  // old: rules => conds                      // an older stored form
  // hard: ['nin']                            // fewer comparisons on top (the lists: only nin)
  // for the dialog:
  what: () => [['kind', N_('Kind')], ['folder', N_('Folder')], ['text', N_('Text')]],
  ops: c => (c.f === 'text' ? ['has', 'nhas'] : ['in', 'nin', 'empty']),
  vals: (c, conds) => (c.f === 'kind' ? [['pdf', 'PDF'], ['img', tr('Image')]] : folders().map(p => [p, p])),
  // extra, key, fresh, add, prep, unit, keep: see the head of fltdlg.js
};
const n = docs.filter(d => kflt_match(d, rules, DOC_FLT)).length;
await loadModule('fltdlg');
kflt_dialog({cat: DOC_FLT, rules: f.rules, name: f.name, title: tr('Edit filter'),
  count: r => trn('{0} document matches', '{0} documents match', docs.filter(d => kflt_match(d, r, DOC_FLT)).length),
  save: async (name, rules, md) => { /* the area's save route */ md.remove(); }, del: f.id ? async md => { ... } : null});
```

On the server the area passes one function per condition: `kflt_where(rules, cnd -> (sql, args) | None)` for a list in SQL
(every value a parameter; the area's own `WHERE` keeps deciding what the person may see, a filter only narrows it) or
`kflt_match(item, rules, cnd -> test | None)` in memory. The two sides mean the same; a test of the area checks both with
the same rules.

Who uses it: the lists' saved filters and shared views (catalog `FLT_TASKS` in views.js + `flt_cat` in fltdlg.js, server
`lists/filterrules.py`), the newsletter segments (newsletter.js `nwl_segEdit`, server `newsletter/sync.py nwl_match`), the documents' saved views
(2.857.0, #5518: catalog `dcv_cat` in docviews.js, server `docs/dfilter.py dvf_where` -- every condition built from the
documents search's own `dsr_filters`, matched on the server only, the dialog's count asks `POST /api/docs/views/count`). Tests:
`tests/p2846_a_filterkern_test.py` (the core, the lists' API), `tests/p2846_a_filterkern_ui.js` (the dialog with a stand-in catalog).

## Gestures: swiping a row, leafing (2.876.0, #5559)

A row that does something when a finger swipes it sideways (complete, a short menu, remove, reply ...) builds **no touch
handling of its own**. It hands the shared row swipe what the row does:

- browser, at every start: `static/js/rowswipe.js` -- `rsw_attach({at, can, min, max, go, out, look, lock, done, busy})`,
  `rsw_back(el)`, `rsw_busy()`, `rsw_later(key, fn, box)`

```js
rsw_attach({
  at: e => e.target.closest?.('.myrow') || null,  // the row under the finger, null = no swipe here
  can: dir => dir > 0,                            // 1 = to the right, -1 = to the left
  min: el => 90, max: 120,                        // the threshold; max = a rubber band past it (else the row follows)
  out: (el, dir) => true,                         // past the threshold: the row glides out (else it springs back)
  look: (el, dx, on) => { /* the area's marks while it moves, dx 0 = cleared */ },
  go: (el, dir) => { /* the action */ },
});
```

The rules are the same for every row: 10 px and clearly sideways before it is a swipe (up / down stays scrolling), 24 px at
the screen's edges stay the phone's Back gesture, a finger held still (500 ms, the long press) or `busy()` (a drag) is no
swipe, a light vibration at the threshold, a touchcancel does nothing, the click right after a swipe opens nothing, reduced
motion = no gliding. A live redraw while the finger is on such a row waits: `rsw_busy()` holds the view (liveparts.js
`lpHold`), a part of the page that redraws itself asks `rsw_later(key, fn, box)` first and is drawn after the finger is up.

Who uses it: the task row (dnd.js: right = completed, left = the short menu), the news (collab.js: either side removes),
the swipe to reply on a message (collab.js: chat, team chat, agent chat, comments). Tests: `tests/p2876_a_rowswipe_ui.js`.

Leafing with a swipe (the next / previous document or picture: the full screen of a document, the image viewer, the task
panel) is the other gesture of the core: `static/js/swipenav.js` -- `swn_attach(root, {area, can, go, peek})`. The calendar's
gestures (calgest.js) are their own.

## Calm view: a redraw keeps the reading place (2.924.0, #5224)

The view moves only when the person makes it move; a jump the person asked for (a link, a search hit, "go to ...") is one
calm jump. A new area does not keep scroll positions itself:

- `keepReading(el, fn)` (static/js/render.js) runs `fn` (the redraw) and keeps the element with a key (`id`, `data-k`,
  `data-id`, ... as the morph matches them) at the top of what is in sight on its screen position; no key in sight = the old
  pixel offset, the very top stays the top. `renderView` (so every live delta, `lpMorphView`), `fl_set`, the search results
  and the detail panel use it; a part drawn into a box of its own: `fl_set(box, html)` (it finds the scrolling box).
  Give rows and cards a key - that is what keeps them in place (and what the morph keeps as the same node).
- The browser's own anchoring (`overflow-anchor: auto` on `#view`) stays on; never set `scrollTop` back to a saved pixel
  value after a redraw (that undoes it).
- A focus given back after a redraw: `focus({preventScroll: true})`.
- `tools/check_scrolljump.py` (CI lint) is red for a NEW `scrollIntoView` / `scrollTo` / `scrollBy` / `scrollTop =` /
  `focus()` without `preventScroll` outside a dialog; a jump the person asked for carries `// sprung-ok: <reason>`. The
  places from before are the baseline `tools/scrolljump_baseline.json` (only shrinks, `--update`).
